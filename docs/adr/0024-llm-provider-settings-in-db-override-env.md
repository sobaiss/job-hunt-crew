# LLM provider settings in Postgres override the environment, field by field

Which LLM backend the Analysis context runs on, and every parameter it needs, lived only in environment variables — `LLM_PROVIDER`, `LLM_MODEL`, `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`/`OPENROUTER_API_KEY`/`HF_TOKEN`, `OLLAMA_BASE_URL` — so changing model or rotating a key meant a redeploy. We're adding an Administrator-editable `LLMProviderSetting` in Postgres that takes precedence, resolved **field by field**: the stored value if present, else that field's environment variable, else the provider's hardcoded default. The environment is kept as a fallback rather than replaced.

This deliberately contradicts [ADR 0014](./0014-plan-scoped-quotas-replace-env-var-caps.md), which removed the env-var quota caps outright rather than layering the new system over them, "so there's a single source of truth for every limit rather than two competing ones." The starting states differ, and that's what flips the answer: every `PlanQuotaDefault` row was seeded for every Plan from the first migration, so nothing was left resolving to an env var. Provider settings start empty and stay empty until an Administrator fills the form, so removing the env path would break every existing deployment at deploy time instead of at an Administrator's choosing.

## Considered options

- **Falling back per provider rather than per field** — an incomplete stored row would hand the whole provider back to the environment. Rejected: a typo in one field would silently swing production onto a different backend, which is a worse failure than the missing field it was meant to paper over.
- **Refusing to run on an incomplete row** — rejected for the same reason in reverse: it turns a half-filled form into an outage. Instead the incompleteness is caught earlier, at activation, which is refused with a 422 naming the unresolvable parameter.
- **Keeping `LLM_PROVIDER` authoritative and treating the table as storage only** — defeats the point; an Administrator could fill the form and still need a redeploy.

## Consequences

- A provider with no stored row is not "unconfigured", it is "environment-driven". Because that distinction is invisible in a table of inactive rows, the Admin screen carries an explicit **"None — follow the environment"** row that is selected by default and names the provider the environment currently resolves to.
- `LLM_MODEL` now governs only the environment-driven mode. Once a row exists, an empty model falls back to that provider's hardcoded default and never to `LLM_MODEL`: one model id shared across providers is meaningless the moment the provider changes (`qwen3.5:latest` reaching OpenAI is a guaranteed failure). A model is meaningful only relative to its provider, which is why each `LLMProviderSetting` carries its own.
- API keys move into Postgres, so they are encrypted at rest (Fernet, under a `SETTINGS_ENCRYPTION_KEY`). Failure is asymmetric on purpose: without the key a write fails loudly rather than pretending to save, while a read treats an undecryptable value as absent and falls back to the environment. A lost or rotated key degrades to the previous behaviour instead of halting every Analysis.
- Resolution happens in the few async pipeline functions that already build a provider from the environment and already hold a database session (extraction, Conversion, the comparison run, generation) — not in each worker handler and not on every LLM call. Every entry point, including Ingestion's extraction, funnels through those, so no handler can be forgotten and silently keep reading the environment while the Admin screen says otherwise. One resolution serves one pipeline step, so a step's comparison and recommendation always share a model (the one `model_used` records). A change takes effect at the next *step* to start, not the next Analysis: under Step Functions each state is its own invocation, so it can land between two steps of the same Analysis. That is harmless — what steps hand each other (a Markdown rendition, a JobOffer's structured data) is provider-neutral.
- `ollama`'s dev-local status and `openrouter`/`huggingface`'s not-yet-vetted status stop being deploy-time facts and become a badge in an Admin table. Nothing blocks activating them in production; the warning is informational.
