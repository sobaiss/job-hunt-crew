# Per-site search adapters replace the declarative filter mapping

`SiteConfig.filterParamMapping` maps one Search filter key to one of a site's parameter names and does nothing else — no value translation, exactly one parameter per filter. Every site actually worth querying needs more than that: France Travail wants an absolute date window where we hold a relative token and INSEE codes where we hold a place name, LinkedIn wants `f_TPR=r604800` for that same token and has no notion of contract duration at all, and HelloWork encodes a location as two solidary parameters (`l` plus a companion region URL) while packing work time and telework into one repeated `t`. So each site in scope gets a Python Site adapter, registered by site key, that takes a Search filter and returns either a URL or a base plus parameters. `build_search_url` stays as the fallback for sites without an adapter, which is what leaves WTTJ, Indeed and Glassdoor working untouched.

## Considered options

A richer declarative structure inside `filterParamMapping` was the obvious first move, and it was rejected: anything expressive enough for HelloWork's two-parameter location and its shared multi-valued `t` is a small programming language stored in a seed file, where no test can reach it. An adapter is asserted against directly — given this Search filter, this exact URL — which is the coverage the seeded mappings never had.

That absence of coverage was not hypothetical. Every mapping in `packages/prisma/prisma/seed.js` was unverified against the live site, and three were wrong: France Travail's `location → commune` fed a region label to a column that only accepts INSEE commune codes, its `remote → travailATemps` named a parameter that does not exist in the Offres d'emploi v2 API (which has no telework criterion at all, so `remote` there is `UNSUPPORTED` by fact rather than by omission), and LinkedIn's `postedWithin → f_TPR` sent `24h` where a seconds count prefixed with `r` was required. The first two were wrong in *value format* as much as in name, which is precisely what a name-only mapping cannot fix.
